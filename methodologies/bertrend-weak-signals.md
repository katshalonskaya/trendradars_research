## 2. Механика

### 2.1 Критерии и показатели

| # | Показатель | Контур | Ярус | Формулировка в источнике | Что именно измеряет |
|---|---|---|---|---|---|
| 1 | Число документов темы в срезе | ТРЕНД | базовый | «its initial popularity is set to the number of associated documents» | Сколько документов временного среза попало в тему |
| 2 | Косинусная близость тем соседних срезов | СВЯЗИ | базовый | «Compute the cosine similarity between each topic embedding» | Одна ли это тема в двух соседних срезах |
| 3 | Время с последнего обновления темы | ТРЕНД | базовый | «∆t is the number of days since τ^k last received an update» | Насколько давно тема пополнялась документами |
| 4 | Popularity (p) | ТРЕНД | производный | «BERTrend estimates topic popularity over time and classifies them into signal categories based on popularity dynamics» | Накопленный вес темы с учётом затухания |
| 5 | Наклон популярности в окне | ТРЕНД | производный | «a positive slope of the linear regression line fitted to the topic's popularity values within the window» | Растёт тема или падает |
| 6 | Пороги P10 и P50 | ТРЕНД | производный | «two empirical thresholds — the 10th percentile (P10) and the 50th percentile (P50) of popularity values within the window» | Границы классов, вычисленные из самих данных |
| 7 | Класс сигнала | ТРЕНД | итоговый | noise / weak / strong | Тип темы |

**Ключевое отличие от Yoon и EScore.** Там объектом оценки было слово из заранее составленного словаря. Здесь объект — тема, которую алгоритм выделил сам (BERTopic: эмбеддинги + UMAP + HDBSCAN), и число тем заранее не задаётся. Дословно: «does not require the number of topics to be specified in advance».

### 2.1.1 Итоговая сводка показателей

| Показатель | Ярус | Что означает | Как получается | Пример автора |
|---|---|---|---|---|
| Число документов темы | базовый | размер темы в срезе | считается из корпуса | срезы по 2 дня для новостей, по 7 дней для arXiv |
| Popularity при слиянии | производный | тема пополнилась | `p_t' = p_{t−1}' + \|D_t'\|` | — |
| Popularity без обновления | производный | тема угасает | `p_t' = p_{t−1}' · e^{−λ·Δt²}` | λ = 0,01 |
| Наклон | производный | направление движения | линейная регрессия популярности по окну | окно 14 дней (в коде) |
| P10, P50 | производный | границы классов | процентили популярности в скользящем окне | — |
| Класс сигнала | итоговый | шум / слабый / сильный | правило из трёх ветвей, см. 2.3.2 | — |

### 2.2 Шкалы

| # | Показатель | Тип шкалы | Диапазон | Как описаны деления |
|---|---|---|---|---|
| 1 | Popularity | числовая непрерывная | от 0 вверх, верхней границы нет | делений нет |
| 2 | Косинусная близость | числовая | 0…1 | порог слияния 0,7; для zero-shot — 0,45 |
| 3 | Наклон | числовая | любой знак | важен только знак: больше нуля или меньше |
| 4 | Класс сигнала | качественная, 3 класса | noise / weak / strong | границы — процентили популярности |

**Шкала порогов — относительная и подвижная.** Пороги пересчитываются на каждом шаге по распределению популярности в скользящем окне. Это тот же приём, что медиана у Yoon, но доведённый до конца: границы адаптируются к скорости потока данных.

### 2.3 Схема расчёта

#### 2.3.1 Дерево вывода показателей

```
документы среза ──► BERTopic (эмбеддинги + UMAP + HDBSCAN) ──► темы среза
                                                                   │
     косинусная близость с темами прошлого среза ◄─────────────────┤
                          │                                        │
            ≥ 0,7 ────────┴──── < 0,7                              │
              │                   │                                │
    p += число новых        новая тема,                            │
      документов            p = число документов                   │
              │                   │                                │
              └─────────┬─────────┘                                │
                        ▼                                          │
     тема не обновлялась ──► p = p × e^(−λ·Δt²)  ◄─────────────────┘
                        │
                        ▼
              Popularity (p) ──┬──► P10, P50 по скользящему окну ──┐
                               │                                   │
                               └──► наклон регрессии в окне ───────┤
                                                                   ▼
                                                          КЛАСС СИГНАЛА
```

#### 2.3.2 Формулы по каждому производному показателю

| Показатель | Формула в источнике | Дословно или реконструкция |
|---|---|---|
| Начальная популярность | `p^k_t = \|D^k_t\|` | дословно |
| Популярность при слиянии | `p^k_t' = p^k_{t'−1} + \|D^k_t'\|` | дословно |
| Популярность при отсутствии обновлений | `p^k_t' = p^k_{t'−1} · e^{−λ∆t²}`, λ = 0,01 | дословно |
| Нижний порог | `P10 = P_all[⌊0.1 · \|P_all\|⌋]` | дословно, из Algorithm 1 |
| Верхний порог | `P50 = P_all[⌊0.5 · \|P_all\|⌋]` | дословно, из Algorithm 1 — **но коду не соответствует, см. 2.6.1** |
| Класс сигнала | правило из трёх ветвей: если `p < P10` → noise; если `P10 ≤ p ≤ P50` и наклон > 0 → weak, иначе noise; если `p > P50` → strong | дословно, раздел 3.5 |

Правило классификации дословно: «If p^k_t < P10, τ^k_t is classified as a "noise" signal… If the topic's popularity has been increasing… τ^k_t is classified as a "weak" signal… If the topic's popularity has been decreasing… classified as a "noise" signal, as it likely represents a previously popular topic that is losing relevance… If p^k_t > P50, τ^k_t is classified as a "strong" signal».

**Смысл средней ветви — самое интересное в методе.** Тема со средней популярностью попадает в «слабые сигналы», только если она растёт. Если она среднепопулярна, но падает, её объявляют шумом, а не слабым сигналом. Дословное объяснение авторов: «This helps filter out fading "weak signals" that are actually strong but declining trends». Ни у Yoon, ни у EScore такого различения нет: там падающее и растущее с одинаковой частотой попадают в одну ячейку.

#### 2.3.3 Этапы процедуры

| # | Этап | Вход | Что делается | Выход | Отсев на этом шаге |
|---|---|---|---|---|---|
| 1 | Предобработка | сырые документы | нормализация юникода, разбиение длинных документов на абзацы | абзацы с привязкой к документу | **да** — выбрасываются тексты короче 100 латинских символов |
| 2 | Нарезка по времени | документы | разбиение на срезы заданной длительности G | срезы | нет |
| 3 | Выделение тем | срез | BERTopic: эмбеддинги all-mpnet-base-v2 → UMAP (5 компонент, 15 соседей) → HDBSCAN (минимальный кластер 2, минимальная выборка 1) | темы среза | практически нет — параметры выставлены на максимальную дробность |
| 4 | Слияние с прошлым | темы среза и накопленные темы | косинусная близость, порог 0,7; при слиянии сохраняется эмбеддинг **первого** появления темы | накопленный набор тем | нет |
| 5 | Расчёт популярности | набор тем | прибавление документов либо экспоненциальное затухание | ряд популярности по каждой теме | нет |
| 6 | Классификация | ряды популярности | процентили по скользящему окну плюс знак наклона | три списка: шум, слабые, сильные | да — по порогам |

**Отсева «по существу» нет ни на одном шаге,** кроме фильтра коротких текстов. Это выгодно отличает метод от Yoon, где топ-500 слов на интервал убивал ровно то, что искали. Здесь в расчёт попадают все темы, а разделение происходит только на последнем шаге и обратимо.

**Сохранение эмбеддинга первого появления** — отдельный приём: «To maintain topic embedding stability, the embedding of the first occurrence of a topic is retained, preventing drift and over-generalization». Тема не «расползается» по смыслу, догоняя новые документы.

### 2.4 Веса

| Поле | Значение |
|---|---|
| Есть ли веса | весов между показателями нет — свёртки нескольких критериев в один балл не происходит |
| Значения параметров | `decay_factor` (λ) = 0,01; `decay_power` = 2; `min_similarity` = 0,7; `granularity` = 2 дня; `signal_classif_lower_bound` = 10; `signal_classif_upper_bound` = 75 |
| Как определяются | фиксированы авторами в конфигурации, пользователь может менять |
| Обоснование весов в источнике | **есть, и это редкость.** Порог слияния 0,7 обоснован исследованием чувствительности: значения 0,5–0,6 дают «threshold collapse» — несколько тем поглощают всё и пороги начинают скакать; значения 0,8–0,95 дают россыпь микросигналов. Размер окна проверен в диапазоне от 2 до 30 дней, влияние признано слабым |

Порог 0,7 — единственный параметр во всех четырёх разобранных методологиях, для которого проведено и опубликовано исследование чувствительности.

### 2.5 Пороги и отсечки

- **Длина текста:** не короче 100 латинских символов. Обоснование: «Documents below this threshold often represent noise (e.g., article endings, incomplete sentences, social media references)».
- **Слияние тем:** косинусная близость 0,7; для zero-shot — 0,45, «to accommodate the vague and incomplete nature of the user-defined topics».
- **Классы сигналов:** процентили популярности в скользящем окне. **По статье — 10-й и 50-й; по коду — 10-й и 75-й.** См. 2.6.1.
- **Наклон:** проверяется знак линейной регрессии; в коде окно жёстко задано в 14 дней.

Абсолютных порогов вида «не меньше N документов» нет ни одного. Всё относительно и пересчитывается на каждом шаге.

### 2.6.1 Сверка статьи с кодом — четыре версии верхнего порога в трёх разных значениях

Единственная возможность настоящей проверки: код открыт. Сверено 2026-08-09 по актуальной ветке `main`.

| Где сказано | Нижний порог | Верхний порог |
|---|---|---|
| Algorithm 1 и раздел 3.5 статьи | 10-й процентиль | **50-й процентиль (P50)** |
| Раздел 4.2 статьи, про исследование чувствительности | «Q1» | **«Q3»** — то есть 25-й и 75-й |
| Схема Figure 1 | «10th centile» | **«Median»** |
| Строка документации в коде, `BERTrend.py` | «10th percentile» | **«90th percentile»** |
| **Фактическая конфигурация, `bertrend_default_config.toml`** | `signal_classif_lower_bound = 10` | **`signal_classif_upper_bound = 75`** |

Нижний порог сходится везде — 10-й процентиль. Верхний назван по-разному **в четырёх местах**, и числовых значений среди них **три**: 50-й процентиль (он же «Median» на схеме — это одна и та же величина, названная двумя способами), 75-й (он же «Q3») и 90-й. Работает 75-й, потому что именно он лежит в конфигурации по умолчанию, а строка документации в том же файле противоречит собственному коду.

Последствие: воспроизвести числа из статьи по опубликованному коду нельзя — доля тем, попадающих в «сильные сигналы», отличается втрое (при P50 сильными объявляется половина тем, при P75 — четверть).

### 2.6.2 Сверка формулы затухания с кодом

Формула из статьи: `p_t' = p_{t−1}' · e^{−λ∆t²}`, где «λ is a constant decay factor (e.g., λ = 0.01) and ∆t is the number of days since τ^k last received an update».

Реализация в `weak_signals.py`, функция `_apply_decay_to_inactive_topics`:

```
periods_since_last_update = time_diff // granularity
decayed_popularity = last_popularity * np.exp(
    -decay_factor * (periods_since_last_update ** decay_power)
)
```

Значения λ и степени совпадают со статьёй (0,01 и 2). **Но Δt в коде — число периодов, а не дней.** При granularity = 2 дня это ровно вдвое меньшее число, а поскольку оно возведено в квадрат, затухание получается в четыре раза медленнее по показателю экспоненты.

Посчитано:

| Дней без обновлений | По коду (периоды, granularity = 2) | По буквальному тексту статьи (дни) |
|---|---|---|
| 4 | 0,961 | 0,852 |
| 10 | 0,779 | 0,368 |
| 20 | 0,368 | 0,018 |
| 30 | 0,105 | 0,000123 |
| 60 | 0,0001 | практически ноль |

**Вывод: формула подтверждается кодом по форме, но не по единице измерения Δt.** По тексту статьи тема теряет 98% популярности за 20 дней молчания, по коду — 63%. Кто пойдёт считать по статье, получит совсем другую картину. **Совпало 2 из 3** элементов формулы: множитель λ и степень — да, единица времени — нет.

### 2.6.3 Третье расхождение: окно проверки роста

Статья говорит, что наклон считается по окну `[t − W, t]`, где W — настраиваемый размер ретроспективного окна (в статье он называется retrospective window size и проверен авторами в диапазоне от 2 до 30 дней). В коде, функция `_is_rising_popularity`, окно задано жёстко: `retrospective_start = latest_timestamp - pd.Timedelta(days=14)`. То есть W влияет на расчёт порогов, но не на проверку роста, хотя по статье должен влиять на оба.

### 3.1.1 Проверка заменителей на непересечение

| Параметр A | Параметр B | Единицы A | Единицы B | Пересекаются? |
|---|---|---|---|---|
| Popularity | Наклон популярности | накопленные документы | документы за единицу времени | **нет** — уровень и производная. Правильная пара |
| Popularity | Время с последнего обновления | документы | дни | **нет по единицам**, но связаны по смыслу: время без обновлений уменьшает популярность через затухание. Это не двойной счёт, а один механизм — время входит в популярность, а не рядом с ней |

Разведение параметров здесь устроено чище всех разобранных методологий: два по-настоящему разных измерения (сколько накоплено и куда движется) и один механизм забывания, встроенный внутрь первого, а не приставленный сбоку.

### 3.3 Работа с неопределённостью

Отдельного показателя уверенности нет. Механизмов четыре:

1. **Затухание вместо удаления.** Тема, переставшая пополняться, не выбрасывается, а медленно теряет вес и может вернуться. Это защита от ложного вывода «сигнал исчез».
2. **Проверка знака наклона перед объявлением слабого сигнала** — отсекает угасающее, которое по уровню похоже на зарождающееся.
3. **Скользящее окно как «forget gate»** — старые значения не влияют на текущие пороги. Дословно: «The sliding window avoids the influence of outdated signals».
4. **Исследование чувствительности к порогу слияния** с описанием режима отказа («threshold collapse»).

Авторы честно признают отсутствие количественной валидации: «Quantitative results about weak signal analysis are very challenging to obtain due to the lack of established metrics… we focus on a qualitative analysis, including retrospective analysis of known outcomes». То есть проверка есть, но ретроспективная и качественная — на известных задним числом событиях вроде ранних упоминаний COVID-19.

Последствие: числа статьи по опубликованному коду не воспроизводятся, доля «сильных сигналов» отличается втрое. `моя оценка:` установлено сверкой с кодом, раздел 2.6.1.
2. **Единица времени в формуле затухания не совпадает с кодом** — в статье дни, в коде периоды. Последствие: буквальное следование статье даёт вчетверо более быстрое забывание, см. таблицу в 2.6.2.

Как и у Yoon, методология не может сказать «сейчас ничего не происходит». Последствие: сравнивать между собой разные корпуса или разные периоды по числу сигналов бессмысленно.
5. **Популярность накапливается и не нормируется на объём потока.** Если поток документов вырос вдвое, вырастут популярности всех тем разом. У EScore и Yoon нормировка на объём корпуса есть, здесь — нет; её роль частично играют относительные пороги, но только частично: при неравномерном потоке внутри окна перекос остаётся. `моя оценка:` в коде деления на объём среза нет.
6. **Количественной валидации нет,** и авторы это признают прямо. Ретроспективный разбор известных событий не отвечает на вопрос, сколько сигналов метод пропустил.

8. **Требует Python 3.13 и вычислений на эмбеддингах** — порог входа заметно выше, чем у формулы на счётчиках слов.

Работает ли в кейсе автора: да; на корпусе NYT метод ретроспективно поднимает ранние упоминания COVID-19 как слабый сигнал.

**Разница между «низким и растущим» и «низким и падающим» — то, чего нет ни у SBS, ни у 4strat, ни у Trendtracker, ни у Yoon.** У Yoon падающая тема со средней частотой попадёт в тот же квадрант, что и растущая, если совпадут значения по осям. Здесь это разные классы, и различие сделано одним знаком регрессии.

### 5.3 Как разделены контуры ТРЕНД и КОНТЕКСТ

Основной расчёт — целиком контур `ТРЕНД`.

Контур `КОНТЕКСТ` реализован единственным механизмом — zero-shot: эксперт описывает интересующую его тему обычными словами, и система сопоставляет с этим описанием каждый документ отдельно. **Важно, что контекст входит не баллом, а запросом.** Он определяет, за чем следить, но не подкручивает числа. Именно поэтому вычислимость от него не страдает.

Это третий встреченный способ вводить контекст, и он отличается от обоих ранее разобранных: у SBS и 4strat контекст — это дополнительные экспертные оценки; у Trendtracker — фильтр корпуса до расчёта; здесь — параллельный канал наблюдения, который работает одновременно с общим расчётом и не заменяет его.

Переиспользование оценки между клиентами: **невозможно** из-за относительных порогов, как и у Yoon.

### 5.4 Что забираем в свою методологию

1. **Разделение «низкое и растущее» против «низкого и падающего» знаком наклона.** Главная находка. Одна проверка знака регрессии решает проблему, которую остальные методологии не замечают: угасающая тема выглядит как зарождающаяся, если смотреть только на уровень.
2. **Затухание вместо удаления.** Тренд, о котором перестали писать, не исчезает из системы, а теряет вес и может вернуться. Экспоненциальная форма `e^{−λΔt^p}` при этом никогда не уходит в минус — в отличие от линейного веса у Yoon, который ломается при 21 интервале.
3. **Пороги из распределения, а не с потолка.** Процентили в скользящем окне вместо числа вроде 1,77. Но забирать надо с добавкой абсолютного порога — иначе, как и у Yoon, доля сигналов фиксируется конструкцией.
4. **Сохранение исходного смысла темы при слиянии.** Эмбеддинг первого появления не обновляется, поэтому тема не расползается по смыслу, догоняя новые документы. Прямой аналог для нас: определение тренда фиксируется при заведении и не переписывается задним числом.
5. **Исследование чувствительности к параметру с описанием режима отказа.** «Threshold collapse» — образец того, как надо обосновывать порог: не «мы выбрали 0,7», а «ниже 0,6 происходит вот такой конкретный сбой, выше 0,8 — вот такой».
6. **Контекст как запрос, а не как множитель.** Приём zero-shot: эксперт говорит, за чем следить, словами, а система сама сопоставляет документы. Ни один балл при этом не вводится руками. Для нашей задачи это способ дать клиенту влиять на выборку, не разрушая сравнимость оценок.
7. **Сверка статьи с кодом как обязательный шаг разбора.** Не приём методологии, а вывод про метод разбора: если код открыт, читать надо код. Четыре версии одного порога иначе не всплыли бы.

**Чего не забираем:**

- **Ненормированную популярность.** Накопление документов без деления на объём потока за тот же период — шаг назад по сравнению с EScore и Yoon, у которых нормировка есть. Берём механизм затухания, но популярность нормируем.
- **Чисто относительные пороги без единой абсолютной отсечки** — та же беда, что у Yoon: нельзя сказать «сигналов нет».
- **Жёстко зашитое окно в 14 дней** — параметр должен быть параметром.
- **Опору на конкретную модель эмбеддингов** без проверки устойчивости результата при её смене.
